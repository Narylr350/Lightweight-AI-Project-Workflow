# Project Work

## 用途

日常主入口。根据用户需求和项目状态判断本轮任务类型，然后以最小范围推进。

不是单纯的写代码入口。必须先判断任务类型，再决定怎么做。

---

## 何时用

除非常简单维护改动外，每次开工的主入口。用户提出任何需求、问题、改动时，先经过这里判断。

---

## 何时不用

- 项目还没基线（无 `.ai/PROJECT.md` 或基线文件不完整）→ 先用 project-init
- 一轮工作刚结束，准备提交 → 用 project-finish
- 未完成工作必须换线程或换 AI，用户明确要求生成交接 → 用 project-handoff
- 多轮失败需要诊断 → 用 project-audit
- 非常简单维护改动（如错别字、`.gitignore` 一行、格式小修）→ 直接做最小修改，不套完整流程

---

## 关键规则

### 开工前必读基线

1. **`.ai/PROJECT.md`** — 决策摘要。确认 Goal、MVP、Non-goals、Seed Tasks，检查当前需求是否与基线冲突。
2. **`.ai/CONSTRAINTS.md`** — 工作规则。确认硬约束、旧工作流权威源处理方式、已接入的执行层 skill。
3. **最近 commit 的 Next 字段** — 找到上一轮留下的交接线索。

按任务需要再读：

- **`.ai/TECH.md`** — 涉及技术方向、架构边界、依赖、平台选择时读。
- **`.ai/VALIDATION.md`** — 需要决定验证方式或进入 finish 前读。

### 上下文锚点按需读取

如果项目级指令或 `.ai/CONSTRAINTS.md` 引用了具体代码、文档或表达锚点，只有本轮任务涉及对应范围时才读取；无关任务不额外加载。全局作者偏好是缺少具体信息时的默认参考，项目事实、项目级指令和用户当轮明确决定优先。不要根据本轮少量措辞重新推导长期作者偏好。

### 读完后必须用 Git 核验

交接信息只是线索，可能过期或错误。开工前必须跑：

- `git status` — 当前工作区状态
- `git log --oneline -10` — 最近提交历史
- `git diff` — 未提交的改动

发现 commit message 说的和 Git 实际不一致时，以 Git 为准。不盲目按 Next 执行。

Next 只是线索，不是路线图。读到 Next 后必须用 `.ai/PROJECT.md` / `.ai/CONSTRAINTS.md` 和 Git 状态过滤：不符合当前基线、已过期、已完成、会扩大范围或改变方向的 Next，不执行，先向用户确认是否更新基线或另开任务。

如果 `git status` 出现本轮新增文件或目录，必须在 work 阶段即时分类：属于本轮成果的才准备进 Git；临时输出、runtime、cache、logs、下载物、本地凭据等删除、归位或补 `.gitignore`；看不出用途时停下问用户，不要留到提交时用 `git add .` 猜。

### 接手未完成工作的本地 handoff

只有用户明确说“继续 / 接手”、指出 `.ai/HANDOFF.local.md`，或说明上一位 AI 因中断留下交接时，才检查和读取该文件；普通新任务不额外加载。

读取顺序：

1. 先完成上面的 `.ai/` 基线读取和 Git 核验。
2. 若 `.ai/HANDOFF.local.md` 存在，通过 [handoff.mjs](../project-handoff/scripts/handoff.mjs) 的 consume 命令接收内容；从实际 skill 安装位置解析脚本路径，不假定它位于目标仓库内：

   ```text
   node "<project-handoff 实际安装目录>/scripts/handoff.mjs" consume --project "<目标项目根>"
   ```

   命令成功输出完整 JSON 内容后删除交接文件，成功退出表示消费完成。为输出提供足够容量，不用过滤 / 截断管道；核对返回内容中的项目路径、分支、HEAD、改动文件和验证结果。失败时按错误处理，不能把它当作已消费；脚本保留读取 / 输出失败或输出期间被更新的交接。
3. handoff 与当前 Git / 文件系统冲突时，以当前事实为准；与用户当前要求冲突时，以用户当前要求为准，并按基线变化规则处理。
4. handoff 的 Next 只是最近接力线索，不自动执行，不视为用户授权，也不能把其中的 AI 推断升级为已确认决策。
5. 接手后先简要说明已恢复的事实、仍不确定的内容和准备继续的最近步骤，再进入执行；不要重复上一位 AI 已有证据覆盖的探索。

消费由脚本负责，不等待提交后再手动清理；消费只表示材料已交付到当前上下文，不表示任务完成。生成新交接仍需用户手动触发，project-work 不得因为工作区脏、额度可能不足或文件存在而自动生成。

### 判断任务类型

读完基线和核验状态后，判断本轮属于哪种任务：

- **新功能** — 实现 MVP 或后续功能
- **修 bug** — 修复问题
- **复盘** — 梳理现状，不改代码（轻量版 audit）
- **黑盒观察** — 运行项目看行为，不改代码
- **文档同步** — 更新 `.ai/` 基线文件或其他文档
- **release 收尾** — 版本发布前的整理
- **提交前整理** — 整理工作区准备提交
- **需求变化** — 用户改变方向
- **继续上次任务** — 按已核验的 commit Next 或本地 handoff 继续。继续前必须先判断上次任务类型；继续不等于默认继续写代码。

### 快速模式：简单任务跳过深度探索

判断完任务类型后，如果任务是**范围明确、改动可预测、用户需求无歧义**的（配置改名、lint 修复、变量同步、单个文件文档更新），跳过深度项目探索（不用读 docs/context、docs/engineering、任务历史记录），直接做。

- 快速模式仍然读 `.ai/PROJECT.md` + `.ai/CONSTRAINTS.md` + git status/log/diff，这是安全和恢复锚点，不能省。
- 跳过的是"探索项目文档理解上下文"阶段，不是 git 核验。
- 只有任务范围模糊或涉及多个模块时才深度探索。让简单任务不因为"先读 5 个文档确认背景"而变慢。

判断完任务类型后，只做最小且清晰的改动。

- 能在不增加职责混杂和长期耦合的前提下改一个文件，不改两个。
- 能加 10 行清晰解决，不做 100 行无关重构；为当前任务守住已有职责边界不算无关重构。
- 不顺手改无关代码。
- 不为"以后可能用到"加功能。
- 尊重原项目工程风格：代码风格、目录结构、命名、技术栈、测试命令、文档语言和语气要跟随项目。但本 pack 的工作流契约仍生效：`.ai/` 基线文件、结构化 commit、Git 核验、Decision Ownership 不被原项目习惯覆盖。
- 验证按风险分级：配置/文档/纯变量名等低风险改动用 targeted 验证（grep、单次命令），不用全量测试。不让验证成本超过改动成本。
- AI 不主动维护被项目 Non-goals 或 pack 工作流排除的文档。但用户明确要求维护的文档，不管是否被 gitignore 都做。

### 结构边界：最小改动不等于继续堆职责

代码组织先以项目事实为准。修改大型、高频或承担协调职责的文件前，按需读取附近模块、局部 `AGENTS.md`、`.ai/TECH.md`、测试和依赖关系，确认现有所有权与边界；不要从文件行数或通用架构偏好直接推导"必须拆"或"必须不拆"。

- 行数、文件大小、方法数量和高频修改只是调查信号，不设固定阈值。真正需要关注的是本次是否新增独立变化原因、拥有独立生命周期的状态、外部 I/O / 平台边界，或可单独验证的领域逻辑。
- 新行为仍属于当前模块的明确职责，并能保持可读、可验证时，留在原处；不要只为缩短文件预先抽取单次 helper 或空壳模块。
- 已存在清晰所有者或依赖方向时，把行为放到对应边界；当前任务确实需要建立局部边界时，只做能降低耦合或改善验证的最小提取，并沿用项目已有命名、导出和生成代码规则。
- 不默认入口或协调层必须很薄，也不因它已经复杂就继续集中所有新职责。只把同一职责拆成多个 partial / 分片文件可以改善浏览，但不能代替所有权拆分。
- 全面清理历史代码、改变整体架构或跨越当前任务边界的重构属于新范围，先说明证据、收益和风险，交用户确认。
- 若结构问题不影响当前任务正确实施，不顺手扩大战线。只有风险已具体影响后续修改或验证时，才在 finish 的 Next / Notes 留下可执行事项，不制造泛化技术债清单。

### 局部知识：把调查结果留在代码旁

实现不只要在当前回合正确，还要让后续维护者能够从仓库恢复必要上下文。

- 当本轮工作依赖或发现了无法从局部代码直接推导的设计理由、不变量、状态转换、并发或时序约束、平台行为、兼容性处理、外部 I/O 契约、失败模式或反直觉修改后果时，在最接近约束生效的位置补充简洁注释。
- 能由测试表达的行为约束优先用测试固定；测试不适合表达的 Why、外部证据、历史原因和修改后果由注释或局部文档保存。必要时两者同时存在。
- 注释说明 Why、必须保持的约束和违反后的后果，不逐行翻译自解释代码。能通过命名、类型和模块边界说清的 What / How 优先由代码表达。
- 工作中付出调查成本才确认的可复用局部事实，不能只留在当前对话或临时日志里。除非属于敏感信息或项目明确禁止，应在本轮修改范围内把它写入相邻注释、测试或模块文档。
- 修改被注释覆盖的实现时同步核验注释；过期、无法验证或与实际行为冲突的解释应更新或删除。
- 注释只记录项目知识，不写用户纠偏原话、AI 推理过程、任务流水账或临时开发状态。
- 只处理本轮触及且已经理解的范围，不为了提高注释数量扫描或重写整个项目。

### 开发方法论与 skill 接入

开发方法论由用户选择（TDD / 自由编码 / 其他 skill），project-work 不强制。

- 如果 `.ai/CONSTRAINTS.md` 记录了已确认接入的执行层 skill（如 TDD / debugging / codebase-design），在 work 范围内使用。
- 如果声明的执行层 skill 当前环境不可用，不要静默跳过，也不要自动换成别的 skill。先说明基线 / 环境不一致；能用 project-work 默认流程安全推进的小任务可以继续，并在 finish 的 Notes/Next 记录；会影响方法或质量边界的任务先让用户选择修复环境或更新 `.ai/CONSTRAINTS.md`。
- 不要默认强制 TDD，也不要禁止 TDD。
- 执行层 skill 只管"怎么做"，用完后回到 work 流程，不要被它接管整个任务流程。完成后按正常流程进入 project-finish。

### 模块交付：先明确结果和路径，再持续推进

跨多轮的功能、模块开发或自动 / 长时任务，开工前先形成简短的模块交付方案；已有有效方案时核验并复用，不每轮重新规划。简单维护沿用快速模式。

方案应说明：

- **结果与完成线**：解决什么问题、用户能完成哪些操作、哪些结果可观察，以及对应验收方式。列明本次支持范围与不做的内容，不能只写模块名称或“实现全部功能”。
- **实现路径与理由**：如何复用现有架构和依赖、各模块负责什么、状态和外部 I/O 由谁拥有、调用如何形成闭环。解释影响长期维护的选择；不需要预先列完整类树或逐文件设计。
- **关键前提**：哪些事实仍影响路径成立。先用有边界的调查或实验验证承重前提，再建设依赖它的实现；普通实现细节可在执行中确定。需要改变已确认方向、范围或验收标准时交用户决定。
- **有限切片与顺序**：每个切片交付什么可验证结果、依赖什么、如何验收；先贯通核心路径，再补完成线要求的边界。不能只按文件、技术层或不断追加内部检查拆解。

实施前核验方案能否形成闭环：现有依赖是否已承担相关能力、职责 / 状态归属是否明确、切片顺序能否尽早取得端到端证据，以及前置检查是否有具体必要性。新承重选择或依赖能力不明时先查官方资料 / 源码或成熟实现；已有明确路径的小修不强制调研。解释选择理由，不能只给一张任务列表后立即开始建设。

明确需求且方案符合现有基线时，简短说明后直接执行，不增加一次形式确认。只有用户尚未决定的关键需求或承重选择才需澄清。自动推进授权不等于替用户决定这些内容。

有运行时目标模式时，将当前目标及其完成条件作为本轮核验锚点，与基线和模块方案对照；冲突先厘清，不自行改写目标或扩大权限。普通对话仍执行同样的模块设计与收敛规则，不要求先调用 project-goal 或启动目标模式。

持续执行时，每个切片结束都对照模块完成线：已满足什么、还缺什么、下一切片解决哪个缺口。新增检查或工作必须对应未满足的验收项或已证实的必要阻塞；说明关联及做到何种程度，不能因“还能检查”不断延长前置链。安全、数据和权限等真实边界仍按实际风险处理。

承重前提被推翻、现有架构无法支持闭环，或剩余工作已不服务原完成线时，停止沿旧计划加补丁，先修订实现路径；修订触及用户决策边界时再确认。不必等多轮失败才重新判断。

验收满足即结束模块；切片测试通过不等于模块完成，缺少实机、外部依赖或操作授权的验收则明确标为待验收 / 阻塞。只有已获授权且不依赖该阻塞的下一模块才可继续，不用旁支研究填补等待，也不自行删减必需功能。

短任务的方案留在对话。长任务需要跨上下文恢复时，将已确认且无法从代码 / 测试恢复的模块完成线和验收方式放入 `.ai/PROJECT.md` / `.ai/VALIDATION.md`，实现路径、有限交付切片及其依赖放入 `.ai/TECH.md`，沿用已有章节，不新增计划文件或任务看板；写入仍遵守基线确认规则。逐轮进度和最近切片通过 commit Next / Notes 交接。恢复工作时用这些内容与 Git 核验已完成结果和剩余缺口，不能只沿最近 Next 继续。

### 任务拆解：交付切片与维护批次

模块开发按上面的可验收切片拆分；范围明确的维护问题按**同类问题合并、不同类问题拆开**处理，不把维护批次规则当成模块计划：

- **同类问题一轮做完。** 判断标准：能不能用同一个验证方式一次性确认全部改对。能 → 同类，一起改、一次验证、一个 commit。不能 → 不同类，分开做。
- 例：3 个文件的 config 变量名漂移 → 同类，一轮做完。1 个 config 漂移 + 1 个路由鉴权策略 → 不同类，分开做。
- **不同类问题各自独立 commit。** 拆完后只执行第一个，其余写进 commit message 的 Next。
- 维护批次拆完后简短列出本轮范围（一句话即可，如"本轮做 A/B，都属于 config 漂移；C 是鉴权策略，下一轮"）。模块开发仍需先明确交付方案，不以一句本轮说明代替。
- 先做能跑通的最小路径，再补边界和细节。
- 平衡点：太粗容易乱和验证不充分，太细浪费 token。同类合并不丢质量，不同类拆开不丢聚焦。

### 分支规则

每轮工作开始前报告当前分支，并判断本轮和分支的关系：

1. **分支目标已完成** → 提示合并回主线。无风险（工作区干净、无冲突、验证通过）直接合并；有风险问用户。合并后回主线继续新任务。
2. **分支目标未完成，继续做** → 继续当前分支。
3. **当前需求与分支目标无关 + 简单维护** → 可以在当前分支顺手做。
4. **当前需求与分支目标无关 + 中等以上任务** → 切回主线或新开分支。
5. **在主线 + 存在未合并的任务分支** → 提示用户是否先合并。

**基线 / init 特例**：`.ai/` 基线更新、project-init / re-init、长期工作规则调整，默认都是项目级变更，不属于"当前需求与分支无关 + 简单维护"。如果当前在任务分支上，必须先确认它是分支专用基线，还是应回到 `main` / `master` 或合并分支后再做；不能在任务分支上不管不顾继续改项目级基线。

**防止分支黏连**：每轮开工都要重新判断当前需求是否仍属于当前分支。不能因为已经在某个 `feat/*` 分支上，就把后续无关需求、重新初始化、文档基线改造都继续塞进这个分支。

**持续推进不合并工作轮次**：目标模式、持续执行或用户授权自动推进，只减少普通执行确认，不改变任务、commit 和分支边界。一次独立提交成功即结束当前工作轮；执行下一切片或后续任务前，重新进入 project-work，核验任务类型、分支关系和模块剩余验收项。Next 只指向交付方案中的最近一步，不替代模块计划或自动延长完成线。

分支创建策略：
- 简单维护改动可直接在 `main`/`master` 做（typo、文档小改、单行配置、低风险变量同步）。
- 中等以上任务建议使用任务分支：`feat/xxx`、`fix/xxx`。
- 高风险、多文件、多轮验证、可能失败或回滚的任务必须使用任务分支。
- 若当前已经在任务分支上，明确说明"继续当前任务分支"，不要重复建分支。

### 上下文压缩应对

AI 无法检测自己是否被压缩。压缩后丢失的信息无法自检恢复。

应对方式不是检测压缩，而是让关键约束不依赖对话记忆：

- 每轮 work 做完就 finish 提交，不留未提交的中间状态。
- work 开头固定读 `.ai/PROJECT.md` + `.ai/CONSTRAINTS.md` + git log + git status + 最近 commit Next，恢复约束和状态。
- 用户在对话中给出的重要约束（不在 `.ai/` 基线文件里的），work 应提示用户是否要写进基线。约束从对话记忆转移到文件后，压缩就丢不了。
- 已否方案、临时妥协等写进 commit message 的 Notes，不靠对话记忆。

### 验证环境处理

work 用到某环境时即时探测（端口探测、命令检测等轻量方式，几秒钟），不可用时按 `.ai/VALIDATION.md` 或 `.ai/CONSTRAINTS.md` 里记录的规则处理。

处理顺序：AI 先尝试修复（启动服务、设环境变量——可逆操作、不问用户）→ 尝试安装 → 确实做不到才提示用户。不把"环境没起"这种执行问题抛给用户决策。

如果 `.ai/` 基线文件没有对应规则，按优先级：不打断用户（AI 先试）> 降级验证方式（如浏览器验证不通过改查静态产物）> 记录阻塞跳过。

### 决策边界：已确认范围自动推进，基线变化停下

- 已确认范围内可以自动推进，不反复确认普通执行步骤。
- 一旦任务会改变目标、MVP、范围、技术方向、长期规则或 `.ai/` 基线，必须停下让用户确认。
- 改动已有产物文档（README、用户文档）的结构或表达方式属于影响项目气质的改动，先确认。小修（修错别字、更新命令、加一行说明）不需要确认。
- "继续"只能继续已确认的 Next 或当前任务边界，不能自动扩大成重构或新方向。

### 需求与基线冲突时停下

如果用户当前需求与 `.ai/PROJECT.md` 基线冲突（要做的事在非目标里，或超出 MVP 范围且方向不同）：

- **不要偷偷改基线**。
- **不要默默按新方向改代码**。
- 停下来问用户：这是临时探索，还是要更新基线？
- 如果是基线变化，建议更新对应的 `.ai/` 基线文件（或触发 project-init 重建）。
- 如果是临时探索，继续做，但提醒用户最后要在 commit message 的 Notes 里标明"偏离基线，待确认"。

如果连续多轮都偏离基线，触发 project-audit。

### 核心原则

详见 `docs/design-principles.md`。重点是：用户当前需求优先于旧计划，但不偷偷改基线；commit Next 和本地 handoff 都必须核验。

## 完成后下一步

有可提交改动且不是非常简单维护改动时，**进入 project-finish**：检查改动、验证结果、生成 commit message。

- 没有可提交改动 → 不需要 finish，直接结束。
- 发现多轮失败或偏航 → 建议触发 **project-audit**。
- 用户需求与基线严重冲突 → 建议触发 **project-audit** 或 **project-init** 重建基线。
- **当 commit Next 表达完成或无后续，且用户没有给出新需求时**，不自己编造新任务。停下来告诉用户当前状态，确认是要扩方向还是结束。

不要在 work 结束后留一个没有 Next 的空档。要么进 finish，要么明确告诉用户当前状态和下一步。
