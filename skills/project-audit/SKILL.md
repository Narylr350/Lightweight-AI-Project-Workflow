# Project Audit

低频复盘诊断工具。默认只分析，不改代码。

## 用途

诊断项目是否跑偏、交接信息是否与事实冲突、是否过度工程化。输出基于证据的判断、可行路径和取舍，交用户决定下一步。

## 何时用

- 多轮失败：连续几轮没解决问题。
- 用户喊停："不对" / "先复盘" / "怎么又这样"。
- release 前：发布前做一次整体检查。
- 新 AI 接手发现材料冲突：`.ai/` 基线文件 / commit message / 代码三者不一致。

## 何时不用

- 正常推进中——用 project-work。
- 只想提交——用 project-finish。
- 没有异常信号时不要常态化审计。

## 关键规则

### 1. 默认只读

- audit 结论是诊断，不是裁决。
- **不直接改代码**。
- **不改 `.ai/` 基线文件**。
- 输出诊断报告 + 建议，交用户决定。
- 发现基线过期 → 建议更新对应的 `.ai/` 基线文件，而非直接改。
- 发现 bug → 在报告里指出，交 project-work 修复。
- 要把 audit 结论固化成长期规则，必须用户确认或有可核验证据。AI 的诊断不能自动变成基线。
- 审计后不要自动修 skill。先区分通用设计缺口、规则冲突、单次输出偏差、外部工具问题；只有前两类才建议修改规则。
- 不要把非本项目的问题写进本项目的 commit Notes 或长期文档。

### 2. 独立观察者与反证

audit 由参与过当前工作的同一个 AI 触发时，它此前形成的解释、推荐和已否方案都只是线索，不能作为审计前提。

- 多轮失败、用户质疑当前路径、承重技术决定存在争议，或当前 AI 参与了被审计方案时，优先使用一个**独立上下文**的子代理 / 审查者做反证审查。低风险、事实明确的 release 核验或文档同步不强制调用。
- 给独立审查者的材料只包含：用户目标、已确认约束、Git / 文件证据、失败现象和待判断问题。不要把主 AI 偏好的根因、解决方案或辩护当成前提；不要让它继承完整对话后重复当前路径。
- 独立审查者默认只读，任务是寻找反证、其他合理解释、被忽略的层级和真正存在取舍的方案，不直接修改文件，也不替用户决定。
- 主 AI 不默认采信子代理结论。把它视为外部反馈，回到 Git、文件和可复现实验核验后再综合判断。
- 默认一次有边界的独立审查即可；只有问题确实跨越不同专业领域时，才考虑增加不同视角，避免为了显得全面制造 token 消耗。
- 运行环境没有独立审查能力时，执行**观察者重置**：先暂时搁置自己此前的结论，从事实重新列出能够解释现象的不同假说，再主动寻找能推翻每个假说的证据。不要只寻找支持原方案的材料。

### 3. 按需外部调研

audit 不是只在仓库内部循环推理。遇到以下情况时，先明确要解决的未知，再查询外部资料：

- 问题涉及陌生领域、框架 / 库选择、标准、平台行为或随版本变化的生态事实。
- 仓库里存在多个合理方案，需要了解成熟项目如何处理真实取舍。
- 当前解决方案明显依赖 AI 经验判断，仓库证据不足以支持“应该这样做”。

优先使用官方文档、源码、标准、研究资料和有代表性的成熟项目。调研结果仍然只是候选证据：必须说明它解决了什么未知、是否适合当前项目，不能把通用最佳实践直接当成本项目决定。

如果问题已经能由本地 diff、配置、日志或可复现实验确定，不为了形式联网；在报告里直接说明为什么不需要外部调研。

### 4. 检查 10 项

1. **是否跑偏**：最近若干 commit 做的事是否符合 `.ai/PROJECT.md` 的目标、MVP、Non-goals？是否触碰了非目标？
2. **文档是否过期**：`.ai/PROJECT.md` / `.ai/TECH.md` / `.ai/CONSTRAINTS.md` / `.ai/VALIDATION.md` 是否还和代码实际一致？
3. **handoff 是否和 Git / 验证证据冲突**：commit message 的 Why / What / Verify / Next / Notes 是否与 `git log` / `git diff` 和实际验证结果一致？Verify 的结论是否超过证据覆盖范围，例如用构建或单元测试声称视觉、交互、性能、平台集成或真实外部 I/O 已整体完成？
4. **是否重复走已否方案**：是否有 commit 的 Notes 记录了已否方案，但后续又在重做？
5. **是否过度工程化**：是否引入了 MVP 不需要的复杂度（第三方库 / 抽象层 / 配置项）？
6. **流程规则是否跨入口覆盖**：如果失败和 workflow / skill 规则有关，检查是否只在某个入口写了规则，但其他入口仍能改同一类事实或绕过同一决策点。不要只修当前触发的 skill，要找出所有能触发同类动作的入口。
7. **维护表面是否与代码脱节**：README、CHANGELOG、版本文件、配置示例、API 文档、CLI help、安装说明等是否和最近代码改动一致？代码改了但维护表面没同步是常见缺口。
8. **产物是否混入非项目内容**：代码、README、用户文档、产品文案中是否混入了用户纠偏原话、AI 失败过程、AI 自我警告、内部设计讨论？这些属于交接层（commit Notes），不属于产物层。
9. **项目表达是否偏离已确认锚点**：只有项目级指令、`.ai/CONSTRAINTS.md` 或现有产物中存在明确表达锚点时才检查。使用通用模板、标准表达或平均做法本身不算问题；只有它覆盖了已确认的作者 / 项目选择，或未经确认改变了已有项目表达时，才算漂移。没有明确锚点时跳过，不从少量对话推导作者气质。
10. **代码质量、结构与局部知识漂移**：最近改动是否引入 warning、error、过时 API、潜在 bug，或违反项目已定义的模块所有权、依赖方向和局部规范。大型、高频文件只作为调查信号；只有出现多个独立变化原因、跨边界职责或验证困难时，才报告结构热点。只有同一区域被反复误解、关键约束只能从对话或历史提交恢复、已知坑未在相邻代码 / 测试 / 局部文档留下线索，或注释与实际行为冲突时，才报告局部知识缺口；不检查注释覆盖率，也不要求给自解释代码补注释。audit 只给证据和影响，不自动要求拆分、重构或全仓补注释。如果 `.ai/CONSTRAINTS.md` 声明了代码质量检查 skill，调用它；否则用 `.ai/VALIDATION.md` 里的验证命令做基本检查或跳过。

### 5. 输出格式

诊断报告包含：

- **触发原因**：为什么做这次审计。
- **观察方式**（条件触发）：是否使用独立审查者；如果没有，如何完成观察者重置。简单且事实明确的审计可省略。
- **现状（Git 核验）**：最近 commit / `.ai/` 基线 / 代码实际状态。
- **问题**：逐条列出发现的问题，对应 10 项检查。
- **判断与证据**：区分已核验事实、候选解释、反证和仍未知的信息。只有证据足够时才写“根因”；否则保留为待验证假说，不用确定语气掩盖未知。
- **外部调研**（条件触发）：说明查询的问题、关键来源、得到的候选做法及其对当前项目的适用性。
- **可行路径与取舍**：存在真实分歧时，比较能实际解决问题的路径，包括继续观察 / 不修改、局部修复、调整 skill、采用成熟方案或重新设计。按项目适配度、影响范围、成本、风险和可逆性说明取舍；证据明确只有一种合理修复时，不为凑数量制造方案。
- **推荐**：可以基于证据推荐一条路径并说明理由，但推荐不是决定，也不默认把问题导回现有 workflow 内补规则。
- **Skill 效果评估**（条件触发）：如果本次对话使用了 `.ai/CONSTRAINTS.md` 声明的 skill，评估其效果：是否帮到任务、有无误报漏报、是否拖慢流程。给出建议：继续用 / 换 / 删 / 加新 skill。不自动改 CONSTRAINTS，交用户决定。

范例见 `docs/examples.md`。

### 6. 完成标准

- 每个主要问题都有仓库事实或可复现实验支撑，推断和未知已明确标注。
- 路径依赖分支触发时，已经完成独立审查或观察者重置，不能由主 AI 原样复述自己此前的判断就结束。
- 已判断是否需要外部调研；需要时已经围绕具体未知查询，不需要时有本地证据说明原因。
- 推荐方案没有超出证据覆盖范围，真实存在的替代路径和取舍没有被当前 AI 的既有方案遮蔽。

### 7. 核验方式

所有结论必须基于 `git log` / `git status` / `git diff` 和文件实际内容。不要基于"印象"或"上次对话说的"下结论。

## 完成后下一步

把诊断报告交给用户决定，不默认把所有问题导回 workflow 内补规则。下一步可能是：

- 证据不足或风险很低 → 继续观察，暂不修改。
- 已确认局部实现问题 → 回 project-work 做最小修正。
- 项目方向或长期基线已经变化 → 回 project-init / re-init 重新确认。
- 外部未知仍决定方案 → 先完成针对性调研或实验。
- 当前设计已经合理 → 结束审计，不为了留下 Next 制造任务。
